### LLD for Seat Locking

```
class LockManager {
    Map<seatId, LockToken> lockMap;

    bool acquire(seatId, userId):
        if seatId not in lockMap:
            lockMap[seatId] = token(userId, timestamp)
            return true
        else:
            return false

    void release(seatId):
        lockMap.remove(seatId)
}
```

### Seat Lock Timeout

A scheduled thread removes locks after 5 minutes.

```
class SeatLockExpiryDaemon extends Thread {
    run():
        while(true):
            for lock in lockMap:
                if lock.timestamp + 5min < now:
                    release(lock.seatId)
            sleep(1min)
}
```

✔ Ensures multi-thread safety
✔ Prevents stale locks
✔ Avoids deadlocks

# 7️⃣ **SEAT BOOKING PSEUDOCODE (MULTITHREAD SAFE)**

```
class BookingService {

    LockManager lockManager;

    Booking bookSeats(userId, showId, seatIds):

        // Step 1: Lock all seats
        for seatId in seatIds:
            if !lockManager.acquire(seatId, userId):
                releaseAll(seatIds)
                throw SeatUnavailableException

        // Step 2: Create booking object
        booking = new Booking(PENDING)
        save(booking)

        // Step 3: Initiate payment
        payment = PaymentService.initiate(booking)

        if payment.success:
            booking.status = CONFIRMED
            for seatId in seatIds:
                mark seatId as BOOKED
                lockManager.release(seatId)
        else:
            booking.status = CANCELLED
            releaseAll(seatIds)

        return booking
}
```

# ✅ **Why must the same `LockManager` instance be shared?**

## 🔹 **Reason 1: Centralized Locking**

If multiple threads handle booking requests, they must all check **one shared lock map**:

```
seatId → lockToken
```

If each thread creates its own LockManager instance:

* Thread A locks seat A1
* Thread B also locks seat A1 because it has a different LockManager instance

❌ This breaks seat consistency
❌ Users can double-book the same seat

Therefore, you need **one global LockManager**.

---

# ✅ **What if the application is distributed (multiple servers)?**

In a single-server application:

* Use a **singleton** LockManager shared across all threads.

In a multi-server / microservice architecture:

* You cannot rely on in-memory LockManager because each server has its own memory.
* Instead you use a **distributed lock store**:

### Common choices:

* **Redis SETNX** locks
* **Zookeeper lock**
* **Etcd locks**
* **Database row-level locks**

This ensures all servers see the **same lock state**.

---


# 🚦 **Thread-Safety Requirement**

Even with a shared LockManager, it MUST be **thread-safe**:

### Using `synchronized` method:

### Or using a `ConcurrentHashMap`:

# 🔐 **What is Distributed Locking?**

Distributed locking ensures that when **multiple servers or instances** access the same shared resource (e.g., seats), **only one server can lock a resource at a time**.

### ✔ Prevents double-booking

### ✔ Ensures thread safety across multiple machines

### ✔ Maintains data consistency

---

# ❗ Why do we need Distributed Locking in BookMyShow?

Let’s say you have:

* **Server 1** handles User A
* **Server 2** handles User B

Both users select seat A1 at the exact same moment.

If locking is **in-memory only**:

* Server 1 LockManager locks A1
* Server 2 LockManager ALSO locks A1
  (because they have different memory → different LockManager instances)

❌ Seat gets double-booked
❌ Catastrophic business failure

Thus, locking MUST be **centralized**.

---

# 🏦 Where do we store distributed locks?

## **Common systems to store locks:**

1. **Redis** (most popular)
2. **Zookeeper**
3. **Etcd**
4. **Database row-level locking (SQL SELECT FOR UPDATE)**

Each one allows all servers to communicate through a **shared locking layer**.

---

# 1️⃣ Redis Distributed Lock (Most Common)

Redis provides atomic operations like **SETNX** (Set if Not Exists).

### ✔ Fast

### ✔ Atomic

### ✔ Designed for distributed locks

### ✔ Used by Uber, Netflix, Amazon, BookMyShow-like systems

---

## ⭐ Redis Locking Flow (SETNX)

### Step-1: Attempt to Lock Seat

```
SETNX seat_123 locked_by_user_7
```

### Outcomes:

* If seat_123 was not locked → Redis returns **1** → Lock acquired
* If already locked → Redis returns **0** → Cannot lock

---

## ⭐ Add Expiry (to prevent stuck locks)

```
SET seat_123 locked_by_user_7 NX PX 300000
```

* **NX** = Only set if key does not exist
* **PX 300000** = Expire after 5 minutes

This ensures locks auto-release.

---

## ⭐ Unlock Flow

```
DEL seat_123
```

But only the owner should unlock it.

### Secure unlock approach:

Use a Lua script to ensure atomicity:

```
if redis.get(key) == user_id then
    redis.del(key)
end
```

# 2️⃣ Zookeeper Distributed Lock

Zookeeper uses **ephemeral nodes**.

### Steps:

1. Try to create `/locks/seat_123`

3. If exists → wait until it is deleted
4. On disconnect, ephemeral node auto-deletes
   → lock automatically released

### ✔ Very reliable

### ✔ High consistency

### ❌ Slower than Redis

Works well for high-scale systems.

# ✅ **What is DB Row-Level Locking?**

**Row-level locking** means the database locks **specific rows** so no other transaction can modify them until the lock is released.

It prevents **two users from modifying the same row at the same time** (like booking the same seat).

---

# 🎯 Why use it in BookMyShow?

When two users pick the same seat:

* User A → locks row for seat A1
* User B → tries to lock row for seat A1
  → but must wait or fail

Thus, the seat is NOT double-booked.

---

# 1️⃣ **How DB Row Locking Works (in SQL)**

## **Core idea**

When you run this:

```sql
SELECT * FROM seats 
WHERE seat_id = 101 
FOR UPDATE;
```

The DB does:

1. Reads the row
2. Locks it exclusively
3. Prevents others from locking or updating the row until transaction commits

---

# 2️⃣ **Real Booking Workflow Using SQL Row Locking**

Let’s say seat table:

| seat_id | show_id | status |
| ------- | ------- | ------ |
| 101     | 55      | FREE   |

---

## ⭐ Step 1: Begin transaction

```sql
BEGIN;
```

---

## ⭐ Step 2: Lock the seat

```
SELECT * FROM seats 
WHERE seat_id = 101 AND show_id = 55
FOR UPDATE;
```

### What happens:

* If the seat is not locked:

  * Row is locked for **this transaction only**
* If another transaction already locked it:

  * Your query **waits** (blocking)
    OR
  * Returns **lock timeout** (if configured)

---

## ⭐ Step 3: Check seat status (inside app logic)

If seat is already booked:

```
status = 'BOOKED' ⇒ fail booking
```

Else continue.

---

## ⭐ Step 4: Update seat status

```
UPDATE seats
SET status = 'LOCKED'
WHERE seat_id = 101;
```

---

## ⭐ Step 5: Commit the transaction

```
COMMIT;
```

* Lock is released
* Seat becomes ‘LOCKED’ and visible to others

---

# 3️⃣ **How Does Concurrency Get Solved?**

### User A and User B try to lock seat 101:

**User A:**

```
SELECT ... FOR UPDATE;  → Lock acquired
```

**User B:**

```
SELECT ... FOR UPDATE;  → Waits (blocked)
```

If User A commits:

* User B then proceeds and sees seat = LOCKED
* User B's booking fails

**Thus → No double booking**

# 4️⃣ Types of Row Locks

| Command                 | Description                                  |
| ----------------------- | -------------------------------------------- |
| **SELECT … FOR UPDATE** | Exclusive lock → blocks others               |
| **SELECT … FOR SHARE**  | Shared lock → others can read but not update |
| **UPDATE/DELETE**       | Automatically acquires exclusive row lock    |
| **INSERT**              | Locks new row until commit                   |

---

# 5️⃣ **Isolation Levels that Affect Row Locking**

| Isolation Level      | Behavior                           |
| -------------------- | ---------------------------------- |
| **Read Uncommitted** | No locks (not safe)                |
| **Read Committed**   | Row locked until statement ends    |
| **Repeatable Read**  | Rows locked until transaction ends |
| **Serializable**     | Highest safety, slowest            |

For BookMyShow use:

👉 **Repeatable Read**
OR
👉 **Serializable** (if low volume)

```java
public boolean lockSeat(int seatId) {
```

# 🔒 **What is @Lock(LockModeType.PESSIMISTIC_WRITE)?**

`@Lock(LockModeType.PESSIMISTIC_WRITE)` is a **JPA annotation** used in Spring Boot to tell Hibernate:

> **Lock the selected database row(s) for writing — block others from modifying or reading them until the transaction completes.**

This is how Spring Boot performs **row-level locking** → same as:

```
SELECT ... FOR UPDATE
```

in SQL.

It is used to prevent **race conditions**, such as:

* Two users booking the same seat
* Two threads updating the same inventory
* Multiple payments modifying the same wallet balance

---

# 🎯 Why call it “Pessimistic Write Lock”?

Two strategies exist: **Optimistic** vs **Pessimistic**.

## Pessimistic Lock:

* Assumes **other users WILL conflict**
* Locks the row immediately
* Prevents others from reading/updating
* Blocking lock

Used for: **Seat booking, inventory, money transactions**

---

# ✔ What exactly happens when you use `@Lock(PESSIMISTIC_WRITE)`?

When Spring Data executes a query marked with:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

Hibernate generates SQL like:

```
SELECT * 
FROM seats 
WHERE id = ?
FOR UPDATE;
```

This does 3 things:

### 1️⃣ Locks row exclusively

* Only **one transaction** can hold the lock
* Any other transaction must **wait**

### 2️⃣ Prevents updates by other threads

Row cannot be modified by other transactions until lock is released by COMMIT or ROLLBACK.

### 3️⃣ Ensures atomicity

Perfect for **avoiding double booking**.

---

# 🔧 Example in Repository

```java
public interface SeatRepository extends JpaRepository<Seat, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT s FROM Seat s WHERE s.id = :seatId")
    Seat findSeatForUpdate(@Param("seatId") Long seatId);
}
```

Generated SQL:

```
SELECT * FROM seats WHERE id = ? FOR UPDATE;
```

---

# 🧠 Why you MUST use @Transactional with it?

Row-level locks only exist **inside a transaction**.

Without `@Transactional`, the lock is acquired and then immediately released (useless).

Correct usage:

```java
@Transactional
public void lockSeat(Long id) {
    Seat s = seatRepo.findSeatForUpdate(id);
}
```

# 🛑 What happens if another thread tries to lock the same row?

Thread A locks seat 101
Thread B tries to lock seat 101

Behavior:

Thread B → **blocked** until Thread A commits.

If lock timeout is set:
Thread B → **QueryTimeoutException**.

This is exactly how **double booking is prevented**.

Use it when:

✔ Data must be **100% consistent**
✔ Conflicts cause serious issues
✔ Multiple users try to update same row
✔ No two users should modify the same resource

Examples:

# 📌 When NOT to use it?

Avoid if:

Spring helps with concurrency using:

* `ReentrantLock`
* `@Transactional`

If there are 5 application servers, the locking is NOT shared.

✔ Fast
✔ Prevents local conflicts

**But another server won’t know about this lock** → double-booking can still happen.

```java
    Seat seat = seatRepo.findSeatForUpdate(seatId);
}
```

Spring sends:

```
BEGIN;
```

---

## ✔ Step 2 — Spring Boot Executes Locked Query

`@Lock(PESSIMISTIC_WRITE)` → Hibernate → DB SQL:

```
SELECT * FROM seats WHERE id = 101 FOR UPDATE;
```

---

## ✔ Step 3 — DATABASE locks the row

Case:

### User A arrives first:

* DB locks seat row (id=101)
* User A proceeds

### User B arrives second:

* DB sees row is locked by User A
* User B must WAIT (or timeout)

This waiting behavior is **REAL concurrency control**.

---

## ✔ Step 4 — User A updates seat

```
UPDATE seats SET status='LOCKED' WHERE id=101;
```

---

## ✔ Step 5 — User A commits transaction

```
COMMIT;
```

Database releases row lock.

---

## ✔ Step 6 — User B now gets the row

But the row status is already:

```
LOCKED
```

So User B → booking fails.

```java
@Entity
```

## 🟦 Repository

```java
public interface SeatRepo extends JpaRepository<Seat, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT s FROM Seat s WHERE s.id = :id")
    Seat findSeatForUpdate(@Param("id") Long seatId);
```

Generated SQL:

```
SELECT * FROM seat WHERE id=? FOR UPDATE;
```

---

## 🟧 Service

```java
@Service
public class BookingService {

    @Autowired
    SeatRepo seatRepo;

    @Transactional
    public boolean lockSeat(Long id) {

        Seat seat = seatRepo.findSeatForUpdate(id);

        if (seat.getStatus() != SeatStatus.FREE) {
            return false;
        }

        seat.setStatus(SeatStatus.LOCKED);
        seatRepo.save(seat);

        return true;
    }
}
```

---

## 🟨 When two users call lockSeat simultaneously

### User A:

→ Lock acquired
→ Seat changed → LOCKED
→ COMMIT

### User B:

→ Waits
→ Reads updated row → sees LOCKED
→ Returns false
