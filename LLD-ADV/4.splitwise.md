# 📌 **CORE IDEA**

Splitwise uses a **Directed Weighted Graph** for balances.

```
A owes B = +50  (Edge: A -> B = 50)
B owes C = +20  (Edge: B -> C = 20)
```

We store balances as:

```
Map<UserId, Map<UserId, Double>> balanceSheet
```

For concurrency: these maps must be **thread-safe** and updates must be atomic.

# 🧠 **CONCURRENT DATA STRUCTURES TO USE**

In Java:

| Need                                          | Data Structure                                 | Reason                        |
| --------------------------------------------- | ---------------------------------------------- | ----------------------------- |
| Concurrent user balance updates               | **ConcurrentHashMap**                          | Lock striping, low contention |
| Atomic add/subtract of balances               | **AtomicDouble / DoubleAdder**                 | Thread-safe arithmetic        |
| Holding multiple internal maps                | **ConcurrentHashMap inside ConcurrentHashMap** | Fine-grained locking          |
| Group expenses modifications                  | **ReadWriteLock**                              | Many reads, few writes        |
| Operations requiring atomic multi-step update | **synchronized blocks** or **StampedLock**     | Consistent graph update       |

We will use:

### ✔ `ConcurrentHashMap<UserId, ConcurrentHashMap<UserId, DoubleAdder>> balanceSheet`

Best combo for multi-threading operations.

# 🧵 **4. SplitwiseService WITH CONCURRENCY**

### Full thread-safe implementation:

```java
public class SplitwiseService {

    // user -> (otherUser -> amount)
    private final ConcurrentHashMap<String, ConcurrentHashMap<String, DoubleAdder>> balanceSheet
            = new ConcurrentHashMap<>();

    public SplitwiseService(List<String> userIds) {
        for (String u : userIds) {
            balanceSheet.put(u, new ConcurrentHashMap<>());
        }
    }

    public void addExpense(Expense expense) {
        String paidBy = expense.getPaidBy();
        
        for (Split s : expense.getSplits()) {
            if (s.getUserId().equals(paidBy)) continue;

            double amount = s.getAmount();

            // debtor → creditor
            adjustBalance(s.getUserId(), paidBy, amount);
        }
    }

    private void adjustBalance(String from, String to, double amount) {

        // ensure inner map exists
        balanceSheet.putIfAbsent(from, new ConcurrentHashMap<>());
        balanceSheet.putIfAbsent(to, new ConcurrentHashMap<>());

        balanceSheet.get(from)
                .putIfAbsent(to, new DoubleAdder());
        balanceSheet.get(to)
                .putIfAbsent(from, new DoubleAdder());

        DoubleAdder owes = balanceSheet.get(from).get(to);
        DoubleAdder reverse = balanceSheet.get(to).get(from);

        synchronized (this) { // atomic multi-step update
            double net = owes.sum() - reverse.sum() + amount;

            // reset both
            owes.reset();
            reverse.reset();

            if (net > 0)
                owes.add(net);       // from owes to
            else
                reverse.add(-net);   // to owes from
        }
    }

    public Map<String, Map<String, Double>> getBalances() {
        Map<String, Map<String, Double>> result = new HashMap<>();

        for (var entry : balanceSheet.entrySet()) {
            String user = entry.getKey();
            Map<String, Double> inner = new HashMap<>();
            for (var e : entry.getValue().entrySet()) {
                if (e.getValue().sum() > 0)
                    inner.put(e.getKey(), e.getValue().sum());
            }
            result.put(user, inner);
        }
        return result;
    }
}
```

---

# 🟡 **5. Why `synchronized` block inside judge?**

Balance update has **multiple steps**:

```
read current forward edge  
read reverse edge  
compute net  
wipe both  
write new result  
```

This MUST be atomic.

**Solution** → minimal locking inside synchronized block
Because:

* The map operations (putIfAbsent) are concurrent
* Only the **netting logic** needs atomicity

This design minimizes lock contention and is production-ready.

# 🧵 **Concurrency in Each Data Structure (Explained)**

## 1. **ConcurrentHashMap**

* Lock striping (locks only bucket-level segments)
* Multiple threads can update different users freely
* Used for both outer map and inner map

Why use it?

* Mutations are concurrent
* Reads have no blocking
* Highly scalable (millions ops/sec)

---

## 2. **DoubleAdder**

* Lock-free, high-performance alternative to AtomicDouble
* Perfect for frequent increments (balance updates)
* Adds are distributed across internal cells → avoiding CAS contention

Why used?

* Expense updates happen frequently
* Leverages multi-core CPU while updating balances

---

## 3. **Synchronized block**

Used ONLY during:

* netting computation
* updating forward/reverse edges

Why?

* Multi-step update must be atomic
* Prevent inconsistent balance graph

# 🟨 **Service Layer (Persistence + Concurrency)**

## Add Expense → Persist + Update in-memory concurrent balance

```java
@Service
public class ExpenseService {

    @Autowired
    private ExpenseRepository expenseRepo;

    @Autowired
    private ExpenseSplitRepository splitRepo;

    @Autowired
    private SplitwiseConcurrentEngine balanceEngine; // from earlier concurrency LLD

    @Transactional
    public void createExpense(Expense expense) {

        // Save expense in DB
        expenseRepo.save(expense);
        for (ExpenseSplit split : expense.getSplits()) {
            splitRepo.save(split);
        }

        // Update the in-memory balance graph
        balanceEngine.addExpense(expense);
    }
}
```
