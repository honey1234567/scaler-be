# 2. **Key Concurrency Strategy**

### **Spot-level locking using `ReentrantLock`**

Each parking spot uses a small lock:

* Prevents two threads from allocating the same spot
* Keeps system highly scalable because only specific spots get locked
* Avoids global locks on floors/parking lot

### **ConcurrentMap for ticketing**

* Ensures thread-safe insert & retrieval

## **Parking Spot (Thread-Safe)**

```java
import java.util.concurrent.locks.ReentrantLock;

class ParkingSpot {
    private final String id;
    private final SpotType type;
    private volatile boolean isFree = true;
    private final ReentrantLock lock = new ReentrantLock();

    public ParkingSpot(String id, SpotType type) {
        this.id = id;
        this.type = type;
    }

    public boolean tryPark(Vehicle v) {
        if (!isCompatible(v)) return false;

        lock.lock();
        try {
            if (isFree) {
                isFree = false;
                return true;
            }
            return false;
        } finally {
            lock.unlock();
        }
    }

    public void free() {
        lock.lock();
        try {
            isFree = true;
        } finally {
            lock.unlock();
        }
    }

    public boolean isCompatible(Vehicle v) {
        return (v.getType() == VehicleType.CAR && type == SpotType.COMPACT) ||
               (v.getType() == VehicleType.BIKE && type == SpotType.BIKE) ||
               (v.getType() == VehicleType.TRUCK && type == SpotType.LARGE);
    }

    public boolean isFree() { return isFree; }
    public String getId() { return id; }
}
```

## **Floor**

```java
class Floor {
    private final int floorNo;
    private final List<ParkingSpot> spots;

    public Floor(int floorNo, List<ParkingSpot> spots) {
        this.floorNo = floorNo;
        this.spots = spots;
    }

    public ParkingSpot findAvailableSpot(Vehicle v) {
        for (ParkingSpot spot : spots) {
            if (spot.isFree() && spot.isCompatible(v)) {
                if (spot.tryPark(v)) {
                    return spot;
                }
            }
        }
        return null;
    }
}
```

## **Parking Lot (Main Service)**

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;

class ParkingLot {

    private final List<Floor> floors;
    private final ConcurrentMap<Long, Ticket> ticketMap = new ConcurrentHashMap<>();
    private final AtomicLong ticketCounter = new AtomicLong(1);

    public ParkingLot(List<Floor> floors) {
        this.floors = floors;
    }

    public Ticket parkVehicle(Vehicle v) {
        for (Floor f : floors) {
            ParkingSpot spot = f.findAvailableSpot(v);
            if (spot != null) {
                long ticketId = ticketCounter.getAndIncrement();
                Ticket ticket = new Ticket(ticketId, spot.getId(), v.getNumber());
                ticketMap.put(ticketId, ticket);
                return ticket;
            }
        }
        return null; // No spot found
    }

    public void exitVehicle(long ticketId) {
        Ticket ticket = ticketMap.remove(ticketId);
        if (ticket != null) {
            // Locate spot and free it
            for (Floor f : floors) {
                for (ParkingSpot spot : f.getSpots()) {
                    if (spot.getId().equals(ticket.getSpotId())) {
                        spot.free();
                        return;
                    }
                }
            }
        }
    }
}
```

Below is a **simple, clear explanation** of why we use **ConcurrentHashMap** and **AtomicLong** in the Parking Lot LLD — with practical examples showing how multiple threads behave.

---

# 🚦 **Why `ConcurrentHashMap`?**

### **Problem: Multiple threads will create & remove tickets at the same time**

Imagine:

* 50 cars entering simultaneously
* Each car is handled by a separate thread
* Every thread needs to **insert a newly generated ticket** into `ticketMap`
* Exit threads will **remove tickets** when vehicles leave

If we used a normal `HashMap`:

❌ It is **not thread-safe**
❌ Two threads modifying it can corrupt internal buckets
❌ Can cause data loss or even infinite loops

Example of race condition with HashMap:

```
Thread A: Put ticketId=10
Thread B: Put ticketId=11   (same time)
```

HashMap may rehash internally → data becomes corrupted.

---

# ✔ **Solution: Use `ConcurrentHashMap`**

`ConcurrentHashMap` allows:

* Multiple threads reading at the same time
* Multiple threads writing to different segments safely
* No locking of entire map

This keeps the parking lot system **fast and safe**.

### Example scenario:

```
Thread 1                   Thread 2
---------                 -----------
ticketMap.put(1, T1);    ticketMap.put(2, T2);
```

Both operations:

* Safe
* Non-blocking for each other
* No corruption

**This is essential because ticket insert/remove happens constantly.**

---

# 🚦 **Why `AtomicLong`?**

### **Problem: Two cars may enter at the same time**

We generate tickets using:

```java
ticketCounter.getAndIncrement();
```

If we used a normal `long`:

```
ticketId = ticketId + 1;
```

Two threads doing this simultaneously may produce:

### Race Condition Example 🚨

```
ticketId = 100

Thread A reads ticketId → 100  
Thread B reads ticketId → 100  

Thread A increments → 101  
Thread B increments → 101  
```

➡ Both cars get **ticket #101** ❌
➡ Duplicate ticket IDs ❌

This breaks the entire system.

---

# ✔ **Solution: Use `AtomicLong`**

`AtomicLong.getAndIncrement()` ensures:

* Only **one thread** increments at a time
* The operation is **atomic** (cannot be interrupted)
* Threads see consistent values

### Example:

```
ticketCounter = 100

Thread A → getAndIncrement() = 100 (counter becomes 101)
Thread B → getAndIncrement() = 101 (counter becomes 102)
Thread C → getAndIncrement() = 102 ...
```

Every thread gets a **unique**, non-conflicting ID.

---

# 🔍 A Simple Real-World Analogy

### **ConcurrentHashMap is like many small lockers**

* Several people can put things into different lockers at the same time
* No one blocks the entire storage room

### **AtomicLong is like a token dispenser**

* Each person presses a button
* Machine gives **next token number** without mistakes
* Even if 10 people press at the same instant, everyone still gets a unique token

# ❗ Key Point:

### **A regular `HashMap` does NOT use locks at all.**

It is **not thread-safe** because **no locking mechanism exists** inside it.

But you may be thinking:

> “If we put a lock around the entire HashMap externally, doesn’t it become thread-safe?”

The answer is:
**Only partially, and it still has problems.**

Let’s break this down.

---

# 🧩 1. **HashMap Itself Has No Locks**

Internally:

* HashMap does **not** use `synchronized` blocks
* HashMap does **not** use `ReentrantLock`
* HashMap does **not** use atomic operations

So if you do this from multiple threads:

```java
map.put(key, value);
map.remove(key);
map.get(key);
```

You can get:

* Data corruption
* Infinite loops
* Lost entries
* Rehash corruption during resize

This is because **internal buckets change while other threads are iterating or resizing**.

---

# 🧩 2. What If **You Add External Lock**?

Example:

```java
synchronized(map) {
    map.put(k, v);
}
```

This seems thread-safe — but only **for those methods you wrap**.

### **But HashMap still has problems:**

---

## ❌ Problem A: Resize corruption

HashMap performs a **rehash** when size grows.

During rehash:

* It moves nodes from old buckets to new buckets
* It changes linked lists → trees → lists
* It updates bucket array

Even if a single put is locked externally, other threads might still:

* Iterate over the map
* Use a method you didn’t lock externally
* Trigger a size change

And they will see **inconsistent internal state**.

### Example:

Thread A (inside your synchronized block):

```
map.put("A", 1);   // causes resize and rehash
```

Thread B (not locked because you forgot):

```
map.get("B");
```

Thread B reads a half-resized map → **corrupted view**.

This is why **locking outside is error-prone**.

---

## ❌ Problem B: Identity locking is easy to break

If two developers lock differently:

```java
synchronized(map) {}       // Dev A
synchronized(this) {}      // Dev B
someLock.lock();           // Dev C
```

Boom — thread safety is gone.

Everything must use the SAME lock,
and that is easy to break in large systems.

---

## ❌ Problem C: External iteration is still unsafe

Example (common mistake):

```java
for (Map.Entry e : map.entrySet()) {  // Thread A
    ...
}
```

Meanwhile Thread B:

```java
synchronized(map) {
    map.put(k, v);
}
```

Thread A still sees structure mutated during iteration →
throws **ConcurrentModificationException** or worse, gets corrupted structure.

---

# 🧩 3. Why `ConcurrentHashMap` Fixes This

### ✔ Fine-grained locks (segments or buckets)

Only small parts are locked, not whole map.

### ✔ Thread-safe resizing

CHM uses special algorithms to resize safely even when other threads are reading/writing.

### ✔ Lock-free reads for most operations

Reads usually don’t lock at all → fast + safe.

### ✔ Fail-safe iterators

CHM’s iterators **do not throw ConcurrentModificationException**.
They work over a *snapshot* of the buckets.

---

# 🔥 Short Summary

| Structure                      | Thread-Safe? | Why                                                        |
| ------------------------------ | ------------ | ---------------------------------------------------------- |
| **HashMap**                    | ❌ No         | No internal locks → race conditions, resize corruption     |
| **HashMap with external lock** | ⚠️ Partially | Works only if every access is locked & resize still risky  |
| **ConcurrentHashMap**          | ✔ Yes        | Built-in fine-grained locking + safe resizing + atomic ops |

---

# ✔ Final Answer (in one line)

**HashMap is not thread-safe because it uses no internal locking, and even if you wrap it with an external lock, rehashing, iteration, and concurrent structural changes can still cause corruption unless every single access is correctly synchronized.**
