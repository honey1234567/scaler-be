## 🎯 What to design — Requirements & Design Goals

Before writing code, let’s list what a “Pen” should model. Example requirements:

* A Pen has some **state/properties**: e.g. ink color, ink level (if refillable), tip type (ballpoint, gel, fountain, etc.), thickness (fine, medium, bold), brand or model name, capped/uncapped state.
* A Pen supports certain **behaviors/actions**: e.g. `write(String text)` (or more abstract: `write(char c)` / `draw(...)`), perhaps `refill()` (if refillable), `cap()` / `unCap()`, maybe `getInkLevel()`, `getColor()`, etc.
* We might want **multiple pen types** (ball-point, gel, fountain, marker …). So design should allow **extensions** without changing existing code (i.e. follow OCP).
* We want good **encapsulation**, avoiding exposing internal state directly.
* We may want to reuse some behavior across pen types, or share code via base class or interface.

Thus our design should follow OOP + principles like **Single Responsibility Principle (SRP)**, **Open-Closed Principle (OCP)**, etc. ([GeeksforGeeks][1])

## 🧰 Basic Java Design: Classes / Interfaces for Pen

Here’s a simple design using interface + concrete classes.

```java
// Define an abstraction for Pen
public interface Pen {
    // properties — via getters
    String getColor();
    double getTipSize();       // e.g. 0.5, 0.7 mm etc
    boolean isCapped();

    // behaviors
    void cap();
    void uncap();
    void write(String text);   // writing some text
}
```

Then a concrete implementation, e.g. a disposable ball-point pen:

```java
public class BallPointPen implements Pen {
    private final String color;
    private final double tipSize;
    private boolean capped;

    public BallPointPen(String color, double tipSize) {
        this.color = color;
        this.tipSize = tipSize;
        this.capped = true;
    }

    @Override
    public String getColor() {
        return color;
    }

    @Override
    public double getTipSize() {
        return tipSize;
    }

    @Override
    public boolean isCapped() {
        return capped;
    }

    @Override
    public void cap() {
        capped = true;
    }

    @Override
    public void uncap() {
        capped = false;
    }

    @Override
    public void write(String text) {
        if (capped) {
            throw new IllegalStateException("Cannot write — pen is capped!");
        }
        // For simplicity, we just print to console
        System.out.println("Writing in " + color + " (tip: " + tipSize + "): " + text);
    }
}
```

If we want a **refillable pen** (ink can run out), we might extend or create another class:

```java
public class RefillablePen implements Pen {
    private String color;
    private double tipSize;
    private boolean capped;
    private double inkLevel;   // 0.0 to 1.0  (fraction)

    public RefillablePen(String color, double tipSize, double initialInkLevel) {
        this.color = color;
        this.tipSize = tipSize;
        this.inkLevel = initialInkLevel;
        this.capped = true;
    }

    @Override public String getColor() { return color; }
    @Override public double getTipSize() { return tipSize; }
    @Override public boolean isCapped() { return capped; }
    @Override public void cap() { capped = true; }
    @Override public void uncap() { capped = false; }

    @Override
    public void write(String text) {
        if (capped) throw new IllegalStateException("Pen is capped!");
        if (inkLevel <= 0.0) throw new IllegalStateException("No ink left!");
        // Simulate ink usage
        inkLevel -= 0.01 * text.length();  // arbitrary use ratio
        if (inkLevel < 0) inkLevel = 0;
        System.out.println("Writing \"" + text + "\" in color " + color + ". Remaining ink level: " + inkLevel);
    }

    public void refill(double refillAmount) {
        inkLevel = Math.min(1.0, inkLevel + refillAmount);
    }
}
```

This is a minimal design. We used an interface (`Pen`) for abstraction so that any number of pen types can be added without changing existing code — satisfying OCP. This also keeps each class focused (SRP).

If needed, we could also add more interfaces, e.g. `Refillable` (for refillable pens), or `Cappable` etc., following **Interface Segregation Principle (ISP)** so that classes don’t implement methods they don’t need. That helps keep the design clean. ([Howik][2])

## Thread safety

Good question — we can extend our “pen” design to be **thread-safe**. The details depend on whether pens are going to be shared among threads (e.g. multiple threads writing using the same pen instance, or refilling, capping, etc.). Here’s a clean approach / design sketch for a thread-safe “Pen” in Java. I’ll point out tradeoffs and which parts need synchronization or immutability.

## 🔎 What “thread-safe” means for a Pen

* If multiple threads share a `Pen` instance simultaneously (calling its methods), we want to ensure that the internal state (e.g. capped/uncapped, ink level, color, tip size) remains consistent. ([InfoWorld][1])
* We want to avoid data races (where two threads interleave modifications producing invalid or unexpected state) and avoid partly modified/inconsistent states being visible to other threads. ([artima.com][2])
* We also want to avoid unnecessary synchronization or locking when possible (for performance), especially if many operations are reads or if the object can be made immutable. ([Oracle Docs][3])

Given that, there are two broad strategies:

1. **Immutable Pen** — once created, its state can never change. Thread-safe by design. ([Baeldung on Kotlin][4])
2. **Mutable Pen with synchronized access / safe encapsulation** — allow state changes (e.g. capping/uncapping, ink consumption, refill) but guard internal state transitions with synchronization or similar concurrency mechanisms. ([artima.com][2])

Which strategy to use depends on whether your “Pen” needs to change (likely yes — pens are stateful: capped/un-capped, ink level etc.). So usually, a **thread-safe mutable pen** makes sense.

## 📝 Example: Thread-Safe Pen Interface + Implementation in Java

Below is a conceptual design of a “thread-safe pen” in Java. I’ll show:

* An interface `Pen` (unchanged)
* A concrete class `ThreadSafeRefillablePen` that supports capping/uncapping, writing (consuming ink), and refilling — and uses synchronization to ensure thread-safety

```java
public interface Pen {
    String getColor();
    double getTipSize();
    boolean isCapped();
    void cap();
    void uncap();
    void write(String text);
    void refill(double amount);  // optional, may throw if not refillable
    double getInkLevel();        // optional status
}
```

```java
public class ThreadSafeRefillablePen implements Pen {
    private final String color;
    private final double tipSize;
    private boolean capped;
    private double inkLevel;

    // lock object for synchronization
    private final Object lock = new Object();

    public ThreadSafeRefillablePen(String color, double tipSize, double initialInkLevel) {
        this.color = color;
        this.tipSize = tipSize;
        this.inkLevel = initialInkLevel;
        this.capped = true;
    }

    @Override
    public String getColor() {
        return color;
    }

    @Override
    public double getTipSize() {
        return tipSize;
    }

    @Override
    public boolean isCapped() {
        synchronized(lock) {
            return capped;
        }
    }

    @Override
    public void cap() {
        synchronized(lock) {
            capped = true;
        }
    }

    @Override
    public void uncap() {
        synchronized(lock) {
            capped = false;
        }
    }

    @Override
    public void write(String text) {
        synchronized(lock) {
            if (capped) {
                throw new IllegalStateException("Cannot write: pen is capped");
            }
            if (inkLevel <= 0.0) {
                throw new IllegalStateException("Cannot write: no ink left");
            }
            // simulate ink usage
            // e.g. consume ink proportional to text length
            double usage = 0.01 * text.length();  // example ratio
            inkLevel = Math.max(0.0, inkLevel - usage);
            // actual writing logic — e.g. output text somewhere
            System.out.println("Writing \"" + text + "\" using " + color + " pen. Remaining ink: " + inkLevel);
        }
    }

    @Override
    public void refill(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Refill amount must be > 0");
        synchronized(lock) {
            inkLevel += amount;
            // maybe cap to some max, depending on design
        }
    }

    @Override
    public double getInkLevel() {
        synchronized(lock) {
            return inkLevel;
        }
    }
}
```

### Why this is thread-safe

* All mutable state (`capped`, `inkLevel`) is private. External code cannot directly modify them. ([artima.com][2])
* All methods that read or write mutable state synchronize on a private lock object, ensuring that only one thread at a time can modify or read state — avoiding data races. ([artima.com][2])
* The `color` and `tipSize` fields are immutable (final or never changed), so no need to protect them. Read-only fields don’t need synchronization. ([InfoWorld][1])
* By synchronizing only on the critical sections (state mutation/read), we minimize locking overhead compared to synchronizing everything. ([artima.com][2])

## 🎯 Alternative/Advanced Approaches & Tradeoffs

* **Immutable Pen**: If you model a Pen whose state never changes — e.g. just a “blue ballpoint pen with 0.7mm tip” and you don’t model ink depletion/capping — you could make the class immutable. Immutable objects are automatically thread-safe. ([Baeldung on Kotlin][4])
* **Lock-free / atomic variables**: For simple mutable fields (e.g. ink level), you might use atomic types (`AtomicDouble` or `AtomicInteger` if representing discreet ink units) to avoid explicit synchronization, though for multiple fields that must be updated consistently (e.g. ink level + capped state), synchronization is easier and safer. ([GeeksforGeeks][5])
* **Minimizing lock scope**: Only lock what’s necessary (e.g. state changes), avoid holding locks while doing heavy work (like actual writing, I/O) to reduce contention — a common guideline for concurrency-safe design. ([artima.com][2])
* **Document thread-safety**: If this is part of a library or shared codebase, you may want to annotate or document which classes are thread-safe, and under what usage constraints (e.g. `ThreadSafeRefillablePen` is safe for concurrent use). Many frameworks/tools rely on such annotations. ([Reddit][6])

## ✅ Summary — When to Use Which Design

| Scenario                                                                                          | Recommended Design                                                       |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Pen with **fixed properties only** (color, tip size; no ink depletion, no cap/un-cap)             | Immutable Pen class — simpler and thread-safe automatically              |
| Pen with **mutable state** (ink level, cap/un-cap, refill, write) — possibly shared among threads | Mutable Pen with private state + synchronized access (as above)          |
| High performance / high concurrency, simple mutable state                                         | Consider atomic variables or lock-free techniques (if operations simple) |
| Complex operations that combine multiple fields (e.g. ink + cap + maybe tracking usage)           | Use synchronized blocks or lock object to maintain consistency           |

## 🎯 Goals & Constraints for Thread-Safe, Scalable Pen

* The Pen’s state (e.g. capped / uncapped, ink level, tipSize, color, maybe refillable or not) may change over time — so pen is **mutable**.
* Multiple threads might share a Pen instance concurrently: e.g. one thread writing, another refilling, another capping/un-capping — so we need to avoid race conditions, ensure visibility of changes, and preserve internal invariants (e.g. ink level ≥ 0, cannot write when capped).
* We want **scalability**: i.e. if many threads use the pen, we want as little blocking / contention as reasonably possible, while preserving correctness.
* We want clean design: encapsulation, maintainability, extensible to different pen types.

## 🔧 Concurrency-aware Design Strategies (for Java)

When designing concurrent code in Java, some generally recommended strategies are:

* **Immutable objects** when possible — thread-safe by default, no synchronization needed. ([designpatternsmastery.com][1])
* **Thread confinement / no shared mutable state** when possible — if an object is only used by one thread, no need for locks. ([Howik][2])
* **Encapsulate mutable state + proper synchronization** when sharing mutable objects across threads. Make all mutable fields private, and guard all state-modifying or state-reading methods / blocks with locks (or other concurrency utilities) so the object always remains in a valid state. ([artima.com][3])
* **Minimize locking scope**, avoid holding locks during heavy operations (I/O, lengthy computations), reduce contention. ([pranaypourkar.co.in][4])
* Optionally, use advanced or lock-free constructs (atomics, concurrent collections, message-passing, etc.) when appropriate. ([Design Gurus][5])

For a “Pen”, since its state is mutable and likely to be shared (in our scenario), we should encapsulate the state and synchronize access carefully — but we can also try to keep locking minimal to avoid performance bottlenecks.

## 🧰 Example Design: Thread-Safe, Scalable Pen in Java

Here’s a design sketch.

```java
public interface Pen {
    String getColor();
    double getTipSize();
    boolean isCapped();

    void cap();
    void uncap();

    void write(String text) throws IllegalStateException;
    void refill(double amount);  // if refillable
    double getInkLevel();        // if tracking ink
}
```

```java
import java.util.concurrent.locks.ReentrantLock;

public class ConcurrentPen implements Pen {
    private final String color;
    private final double tipSize;

    // mutable state
    private boolean capped;
    private double inkLevel;       // e.g. 0.0 .. maxInk

    // lock to guard state
    private final ReentrantLock lock = new ReentrantLock();

    public ConcurrentPen(String color, double tipSize, double initialInk) {
        this.color = color;
        this.tipSize = tipSize;
        this.inkLevel = initialInk;
        this.capped = true;
    }

    @Override
    public String getColor() {
        return color;               // immutable — no lock needed
    }

    @Override
    public double getTipSize() {
        return tipSize;             // immutable — no lock needed
    }

    @Override
    public boolean isCapped() {
        lock.lock();
        try {
            return capped;
        } finally {
            lock.unlock();
        }
    }

    @Override
    public void cap() {
        lock.lock();
        try {
            capped = true;
        } finally {
            lock.unlock();
        }
    }

    @Override
    public void uncap() {
        lock.lock();
        try {
            capped = false;
        } finally {
            lock.unlock();
        }
    }

    @Override
    public void write(String text) {
        lock.lock();
        try {
            if (capped) {
                throw new IllegalStateException("Cannot write — pen is capped");
            }
            if (inkLevel <= 0) {
                throw new IllegalStateException("Out of ink");
            }
            // consume ink proportional to length (example)
            double usage = 0.01 * text.length();
            inkLevel = Math.max(0.0, inkLevel - usage);

            // do write logic (e.g. output, store, etc.)
            System.out.println("Writing: \"" + text + "\" in color " + color
                     + ", remaining ink: " + inkLevel);
        } finally {
            lock.unlock();
        }
    }

    @Override
    public void refill(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Refill amount must be positive");
        lock.lock();
        try {
            inkLevel += amount;
            // optionally cap to max
        } finally {
            lock.unlock();
        }
    }

    @Override
    public double getInkLevel() {
        lock.lock();
        try {
            return inkLevel;
        } finally {
            lock.unlock();
        }
    }

    // Other useful methods, e.g. toString(), equals(), etc. if needed
}
```

### Why this design balances safety and scalability:

* **Immutable fields** (`color`, `tipSize`): no synchronization needed, safe to share.
* **Mutable state** (`capped`, `inkLevel`) are private and only accessed under lock — ensures no data races or visibility issues. This matches classical guidelines: make fields private, and synchronize all critical sections. ([artima.com][3])
* Using **`ReentrantLock`** (vs `synchronized`): more flexible (e.g. can support tryLock, fairness, better diagnostics), can help scalability under high contention if needed.
* Lock scope is minimal — only state-check & update operations are locked; if “writing” involved heavy work (e.g. I/O, long operations), you could consider: capture necessary state under lock, then release lock and perform heavy operation — to minimize blocking.

---

## ⚠ Trade-offs & When This Might Break Down

* Overhead: locking (especially with many threads) introduces overhead compared to single-threaded access. In high-frequency operations, this could become a bottleneck. That’s a general trade-off with synchronization. ([artima.com][3])
* Granularity: If multiple related fields must be updated together (e.g. capped + inkLevel + maybe write history), you must ensure consistency across them — lock must cover all.
* If you expect many “read-only” operations (e.g. checking ink level, isCapped) and few writes — you could optimize further (e.g. use `volatile` for some fields, or read-write locks). But using volatile only works when you don’t need atomic modifications across multiple fields together. ([Medium][6])
* For very high concurrency with heavy contention, more advanced patterns (lock-free, actor/message-passing, etc.) might scale better — but are more complex and risk subtle bugs. ([officialcto.com][7])

---

## 🔄 Possible Alternate Designs & Scalability Variants

Depending on usage pattern, you could choose:

1. **Immutable Pen** — if pen once created doesn’t change (no ink depletion, no capping/un-capping). Then you get thread safety “for free.” ([designpatternsmastery.com][1])
2. **Stateless / Thread-Local Pen** — each thread gets its own pen instance; no shared state → no synchronization needed. Good when pens aren’t meant to be shared. ([Design Gurus][5])
3. **Concurrent / Lock-based Pen** (as above) — good balance of correctness and scalability for shared mutable pen.
4. **Lock-free / Atomic-based Pen** — if state changes are simple (e.g. only ink level decrement, no complex invariants), you could use atomic primitives or compare-and-set loops. More scalable but more error-prone. ([officialcto.com][7])
5. **Message-passing / Actor-style control** — instead of sharing pen instance directly, threads send “commands” (write, refill, cap/un-cap) to a dedicated thread owning the pen. This avoids locks entirely and can scale well under high concurrency. (This is more advanced and often overkill for a simple Pen.)

## ✅ Summary — What to Use When

* If pen state is fixed and immutable → use immutable class (fast, thread-safe by default).
* If you expect shared mutable state but moderate concurrency → use classic lock-based approach (as in `ConcurrentPen` above).
* If high concurrency & many threads contending over pen → consider advanced concurrency strategies (atomics, message-passing, thread-local, or avoid shared state altogether).
* Always encapsulate mutable state, guard it properly, and avoid exposing internal state directly (no public mutable fields).

## ✅ Approach 1: Using ThreadLocal — Thread-Local Confinement

**Idea**: Instead of sharing one `Pen` instance across threads, each thread gets its *own* pen instance. That way there’s no shared mutable state, so no synchronization needed. This is called “thread-local storage / thread-confinement.” ([geeksforgeeks.org][1])

### When to use:

* If logically each thread should operate with its own pen (or independent pen state), e.g. per-request, per-user, per-task.
* If overhead of separate pen per thread is okay.
* If you want simplicity and minimal synchronization cost.

### Sample code sketch

```java
public interface Pen {
    String getColor();
    double getTipSize();
    void cap();
    void uncap();
    void write(String text);
    double getInkLevel();
    // maybe refill, etc.
}

// A concrete pen implementation (same as before, not shared)
public class SimplePen implements Pen {
    private final String color;
    private final double tipSize;
    private boolean capped;
    private double inkLevel;

    public SimplePen(String color, double tipSize, double initialInk) {
        this.color   = color;
        this.tipSize = tipSize;
        this.inkLevel = initialInk;
        this.capped  = true;
    }

    // getters omitted
    @Override public String getColor()   { return color; }
    @Override public double getTipSize() { return tipSize; }
    @Override public void cap()   { capped = true; }
    @Override public void uncap() { capped = false; }

    @Override
    public void write(String text) {
        if (capped) throw new IllegalStateException("Capped");
        if (inkLevel <= 0) throw new IllegalStateException("No ink");
        double usage = 0.01 * text.length();
        inkLevel = Math.max(0, inkLevel - usage);
        System.out.println("[" + Thread.currentThread().getName() + "] Writing " + text +
            " (remaining ink: " + inkLevel + ")");
    }

    @Override
    public double getInkLevel() {
        return inkLevel;
    }
}

// Utility to get a thread-local pen
public class PenFactory {
    private static final ThreadLocal<Pen> threadLocalPen = ThreadLocal.withInitial(
        () -> new SimplePen("blue", 0.7, 1.0)
    );

    public static Pen getPen() {
        return threadLocalPen.get();
    }
}
```

**Usage**:

```java
Runnable task = () -> {
    Pen pen = PenFactory.getPen();  // each thread gets its own pen
    pen.uncap();
    pen.write("Hello from " + Thread.currentThread().getName());

// spawn multiple threads
```

This way each thread uses its own pen object — no shared mutable state → no locks needed. This can scale well as number of threads grows (subject to per-thread overhead).

**Caveat**: If threads are reused (thread pools), make sure to reset or remove the ThreadLocal when done — or you may leak state accidentally. ([Devzery Latest][2])

## 🎭 Approach 2: Actor / Message-Passing Style — Single Pen “Actor”

**Idea**: Instead of sharing mutable pen state across threads, encapsulate pen state inside an “actor.” Other threads don’t operate on the pen directly; they send messages (requests) to the pen-actor (e.g. “write this text”, “refill ink”, “cap/un-cap”), and the actor processes these messages **serially**, one at a time. That means internal state mutations never happen concurrently — eliminating data races or synchronization problems. This pattern is described by the actor model / active object / message-passing concurrency strategy. ([Java Design Patterns][3])

### When to use:

* When you want a *shared logical pen* but avoid locks and shared state issues.
* When you expect many concurrent requests / operations on the pen from different threads, but want to serialize them safely.
* When you want decoupling, asynchronous / queued execution, possibly prioritization, scheduling, etc.

### Sketch of Actor-style Pen in Java

```java
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;

// Message types
interface PenMessage {}

class WriteMessage implements PenMessage {
    final String text;
    public WriteMessage(String text) { this.text = text; }
}

class RefillMessage implements PenMessage {
    final double amount;
    public RefillMessage(double amount) { this.amount = amount; }
}

class CapMessage implements PenMessage {}
class UncapMessage implements PenMessage {}
class GetInkLevelMessage implements PenMessage {
    final java.util.concurrent.CompletableFuture<Double> reply;
    public GetInkLevelMessage(java.util.concurrent.CompletableFuture<Double> reply) {
        this.reply = reply;
    }
}

public class PenActor implements Runnable {
    private final BlockingQueue<PenMessage> mailbox = new LinkedBlockingQueue<>();
    private final Pen internalPen;

    public PenActor(Pen pen) {
        this.internalPen = pen;
    }

    // external API — threads call this to interact
    public void tell(PenMessage msg) {
        mailbox.add(msg);
    }

    @Override
    public void run() {
        try {
            while (true) {
                PenMessage msg = mailbox.take();     // blocking wait
                if (msg instanceof WriteMessage) {
                    internalPen.uncap();   // or assume pen already uncapped elsewhere
                    internalPen.write(((WriteMessage) msg).text);
                } else if (msg instanceof RefillMessage) {
                    internalPen.refill(((RefillMessage) msg).amount);
                } else if (msg instanceof CapMessage) {
                    internalPen.cap();
                } else if (msg instanceof UncapMessage) {
                    internalPen.uncap();
                } else if (msg instanceof GetInkLevelMessage) {
                    double lvl = internalPen.getInkLevel();
                    ((GetInkLevelMessage) msg).reply.complete(lvl);
                }
                // you can handle shutdown, other commands etc.
            }
        } catch (InterruptedException e) {
            // thread interrupted — exit
        }
    }
}
```

**Usage example**:

```java
public static void main(String[] args) {

    PenActor penActor = new PenActor(realPen);
    Thread actorThread = new Thread(penActor, "PenActorThread");
    actorThread.start();

    // From many threads, you only call tell()
    penActor.tell(new UncapMessage());

    penActor.tell(new RefillMessage(0.5));

    // If you need return value:

    penActor.tell(new GetInkLevelMessage(future));
    future.thenAccept(level -> System.out.println("Ink level: " + level));
```

Here:

* The `PenActor` owns the pen state.
* All requests from other threads go through `tell(...)`, serialized in the `mailbox`.
* Only the actor thread manipulates the pen — no locking needed.
* This is essentially the “actor model / active object” concurrency strategy. ([Wikipedia][4])

### Trade-offs:

* Slight overhead: message queuing, context switching via the actor thread.
* If many threads bombard the actor, mailbox may grow — need to handle queue capacity, back-pressure, maybe use thread-pool or multiple actor instances.
* Slight latency vs direct method call — may or may not matter depending on use case.

## 🎯 What is the Actor Model / Actor-Style Control

* In the Actor model, computation is structured in **actors** — independent entities that each hold *private state*, and never share mutable state directly. ([Wikipedia][1])
* Actors communicate **only via asynchronous message-passing** (no shared-memory). ([Wikipedia][1])
* Each actor has a **mailbox (queue)** of incoming messages. It processes messages **one at a time** (serially), updating its own state, sending messages to other actors, possibly spawning new actors — but never allowing others to mutate its state directly. ([University of Colorado Boulder][2])
* Because there is no shared mutable memory between actors, there is no need for explicit locks or synchronization to protect shared state. This dramatically reduces the risk of race conditions, deadlocks, or other concurrency bugs typical in shared-memory multi-threaded designs. ([Wikipedia][3])
* The model scales well: many actors can exist, and they can run concurrently or in parallel (depending on execution model), making it suitable for high-concurrency or distributed systems. ([javadeveloperkit.com][4])

In short: actor-style design replaces shared objects + locks with **autonomous objects + message passing**, making concurrency safer and easier to reason about.

## 🛠 Actor-Style in Java — Example (Simple Actor Implementation)

Below is a minimal Java-level sketch of how one might implement actor-style control — not relying on heavy frameworks, just the core ideas. It shows:

* An `Actor` base class
* A concrete actor (e.g. for a “Pen” or generic actor) processing messages
* Message-passing via a thread + queue

```java
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;

// Define a generic message interface (could be marker)
interface Message {}

// Example messages
class WriteMessage implements Message {
    public final String text;
    public WriteMessage(String text) { this.text = text; }
}

class RefillMessage implements Message {
    public final double amount;
    public RefillMessage(double amount) { this.amount = amount; }
}

// Base Actor
abstract class Actor implements Runnable {
    private final BlockingQueue<Message> mailbox = new LinkedBlockingQueue<>();
    private volatile boolean active = true;

    // send message to this actor
    public void send(Message msg) {
        mailbox.add(msg);
    }

    // stop actor
    public void stop() {
        active = false;
    }

    // the actor’s processing loop
    @Override
    public void run() {
        try {
            while (active) {
                Message msg = mailbox.take();  // wait for message
                onReceive(msg);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    // handle incoming message
    protected abstract void onReceive(Message msg);
}

// Example actor: a simple pen-like actor
class PenActor extends Actor {
    private double inkLevel;
    private boolean capped = true;

    public PenActor(double initialInk) {
        this.inkLevel = initialInk;
    }

    @Override
    protected void onReceive(Message msg) {
        if (msg instanceof WriteMessage) {
            WriteMessage wm = (WriteMessage) msg;
            if (capped) {
                System.out.println("Cannot write: pen is capped.");
            } else if (inkLevel <= 0) {
                System.out.println("Cannot write: no ink left.");
            } else {
                // consume ink
                inkLevel = Math.max(0.0, inkLevel - 0.01 * wm.text.length());
                System.out.println("Wrote: \"" + wm.text + "\"; remaining ink: " + inkLevel);
            }
        }
        else if (msg instanceof RefillMessage) {
            RefillMessage rm = (RefillMessage) msg;
            inkLevel += rm.amount;
            System.out.println("Refilled ink by " + rm.amount + "; now ink: " + inkLevel);
        }
        // could handle cap/uncap messages, etc.
    }

    public void uncap() { capped = false; }
    public void cap() { capped = true; }
}
```

**Usage:**

```java
public class Main {
    public static void main(String[] args) {
        PenActor pen = new PenActor(1.0);
        Thread penThread = new Thread(pen, "PenActorThread");
        penThread.start();

        // From different threads / callers:
        pen.uncap();  // internal state change; careful if accessed concurrently
        pen.send(new WriteMessage("Hello Actor Pen!"));
        pen.send(new RefillMessage(0.5));
        
        // ...later
        pen.stop();
    }
}
```

### Why this qualifies as actor-style:

* `PenActor` has **private state** (`inkLevel`, `capped`), only mutated inside `onReceive`.
* External callers don’t directly change the state; they send messages via `send(...)`.
* The actor loop processes messages **one by one** (serially), so no concurrency within the actor — avoiding race conditions even without explicit locks.
* Actor can run on its own thread; multiple actor instances can operate independently and concurrently.

## 🧠 When to Use Actor-Style vs Shared-Memory Concurrency

| Scenario / Requirement                                                                                 | Actor-Style (Message Passing)             | Traditional Locks / Shared Memory     |
| ------------------------------------------------------------------------------------------------------ | ----------------------------------------- | ------------------------------------- |
| Shared mutable state → risk of race / deadlock                                                         | ✅ Actor avoids this by design             | ⚠ Need careful synchronization        |
| Many concurrent entities / tasks interacting asynchronously                                            | ✅ Actors scale, decoupled, isolated state | ⚠ Shared memory model becomes complex |
| Need fine-grained control of inter-object concurrency, or distributed actor across threads or machines | ✅ Well-suited                             | 🟡 Possible but error-prone / complex |
| Simple, high-performance, lock-free — requirement doesn’t need asynchronous messaging                  | 🟡 Overhead may be unnecessary            | ✅ Shared objects may suffice          |

## ✅ Summary

* Actor-style control is a concurrency model where stateful entities (“actors”) **own their state privately** and interact only via **asynchronous messages** — no shared mutable state. ([Wikipedia][1])
* In Java, you can implement this with threads + message queues (mailboxes) + loop processing, or use actor frameworks (e.g. Akka) that provide more features like dispatchers, fault-tolerance, and scheduling. ([javadeveloperkit.com][4])
* Actor-style makes concurrency easier to reason about (no locks, no shared-memory races), and helps build scalable, modular, maintainable designs — especially when dealing with many concurrent components or tasks.
