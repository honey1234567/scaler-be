## 🎯 What to design — Requirements & Design Goals

Before writing code, let’s list what a “Pen” should model. Example requirements:

* A Pen has some **state/properties**: e.g. ink color, ink level (if refillable), tip type (ballpoint, gel, fountain, etc.), thickness (fine, medium, bold), brand or model name, capped/uncapped state.
* A Pen supports certain **behaviors/actions**: e.g. `write(String text)` (or more abstract: `write(char c)` / `draw(...)`), perhaps `refill()` (if refillable), `cap()` / `unCap()`, maybe `getInkLevel()`, `getColor()`, etc.
* We might want **multiple pen types** (ball-point, gel, fountain, marker …). So design should allow **extensions** without changing existing code (i.e. follow OCP).
* We want good **encapsulation**, avoiding exposing internal state directly.
* We may want to reuse some behavior across pen types, or share code via base class or interface.

Thus our design should follow OOP + principles like **Single Responsibility Principle (SRP)**, **Open-Closed Principle (OCP)**, etc. ([GeeksforGeeks][1])

## 🧰 Basic Java Design: Classes / Interfaces for Pen

Here’s a simple design using interface + concrete classes.

```java
// Define an abstraction for Pen
public interface Pen {
    // properties — via getters
    String getColor();
    double getTipSize();       // e.g. 0.5, 0.7 mm etc
    boolean isCapped();

    // behaviors
    void cap();
    void uncap();
    void write(String text);   // writing some text
}
```

Then a concrete implementation, e.g. a disposable ball-point pen:

```java
public class BallPointPen implements Pen {
    private final String color;
    private final double tipSize;
    private boolean capped;

    public BallPointPen(String color, double tipSize) {
        this.color = color;
        this.tipSize = tipSize;
        this.capped = true;
    }

    @Override
    public String getColor() {
        return color;
    }

    @Override
    public double getTipSize() {
        return tipSize;
    }

    @Override
    public boolean isCapped() {
        return capped;
    }

    @Override
    public void cap() {
        capped = true;
    }

    @Override
    public void uncap() {
        capped = false;
    }

    @Override
    public void write(String text) {
        if (capped) {
            throw new IllegalStateException("Cannot write — pen is capped!");
        }
        // For simplicity, we just print to console
        System.out.println("Writing in " + color + " (tip: " + tipSize + "): " + text);
    }
}
```

If we want a **refillable pen** (ink can run out), we might extend or create another class:

```java
public class RefillablePen implements Pen {
    private String color;
    private double tipSize;
    private boolean capped;
    private double inkLevel;   // 0.0 to 1.0  (fraction)

    public RefillablePen(String color, double tipSize, double initialInkLevel) {
        this.color = color;
        this.tipSize = tipSize;
        this.inkLevel = initialInkLevel;
        this.capped = true;
    }

    @Override public String getColor() { return color; }
    @Override public double getTipSize() { return tipSize; }
    @Override public boolean isCapped() { return capped; }
    @Override public void cap() { capped = true; }
    @Override public void uncap() { capped = false; }

    @Override
    public void write(String text) {
        if (capped) throw new IllegalStateException("Pen is capped!");
        if (inkLevel <= 0.0) throw new IllegalStateException("No ink left!");
        // Simulate ink usage
        inkLevel -= 0.01 * text.length();  // arbitrary use ratio
        if (inkLevel < 0) inkLevel = 0;
        System.out.println("Writing \"" + text + "\" in color " + color + ". Remaining ink level: " + inkLevel);
    }

    public void refill(double refillAmount) {
        inkLevel = Math.min(1.0, inkLevel + refillAmount);
    }
}
```

This is a minimal design. We used an interface (`Pen`) for abstraction so that any number of pen types can be added without changing existing code — satisfying OCP. This also keeps each class focused (SRP).

If needed, we could also add more interfaces, e.g. `Refillable` (for refillable pens), or `Cappable` etc., following **Interface Segregation Principle (ISP)** so that classes don’t implement methods they don’t need. That helps keep the design clean. ([Howik][2])

## 🔧 Enhancements / More Detailed LLD Considerations

If you want to take the design further (for more realistic scenarios), you could consider:

* Add a **`Refillable` interface** to separate refillable behavior from pens that are not refillable.
* Add a **`Capable` interface** (cap/uncap) if some pens don’t have cap (e.g. marker with cap, or automatic click pen).
* Add **exception handling** (e.g. what happens if ink empty, or tip broken).
* Add **status methods**: `getInkLevel()`, `isOutOfInk()`, `isCapped()` etc.
* Add **decorators** or wrappers — e.g. a “FancyPen” that logs usage, or counts number of writes, or a “SecurePen” that requires authentication (if that were a requirement) — using design patterns like Decorator Pattern. The decorator pattern is useful to extend behavior without modifying the base class. ([Wikipedia][3])
* Use **composition over inheritance** if pen features get complicated (e.g. tip type, ink type, refillable vs disposable, cap vs click, etc.) — that helps keep flexibility. ([GeeksforGeeks][4])

If you want, you could also draw a **UML class diagram** (or list of classes/interfaces) to capture the design. A good technique for early design is to use **CRC cards** (Class-Responsibility-Collaboration). Each card: class name, responsibilities, collaborators → helps you think modularly. ([Wikipedia][5])

## ✅ Why This Design Is “Low-Level Design (LLD) Ready”

* We used abstraction (interface) so pen types are easily extensible without modifying existing code — meets OCP and helps maintainable code.
* Each class has clear responsibility: `Pen` interface defines “what a pen can do / what are properties”; concrete classes implement details (SRP).
* We kept coupling low and cohesion high — each class does one job (encapsulation, behavior encapsulation). This aligns with standard OO-design principles. ([GeeksforGeeks][1])
* We allowed for future extensions — e.g. adding new pen types, new behaviors (refill, cap, click, retractable, etc.) — without redesigning the whole structure.

## Thread safety

Good question — we can extend our “pen” design to be **thread-safe**. The details depend on whether pens are going to be shared among threads (e.g. multiple threads writing using the same pen instance, or refilling, capping, etc.). Here’s a clean approach / design sketch for a thread-safe “Pen” in Java. I’ll point out tradeoffs and which parts need synchronization or immutability.

## 🔎 What “thread-safe” means for a Pen

* If multiple threads share a `Pen` instance simultaneously (calling its methods), we want to ensure that the internal state (e.g. capped/uncapped, ink level, color, tip size) remains consistent. ([InfoWorld][1])
* We want to avoid data races (where two threads interleave modifications producing invalid or unexpected state) and avoid partly modified/inconsistent states being visible to other threads. ([artima.com][2])
* We also want to avoid unnecessary synchronization or locking when possible (for performance), especially if many operations are reads or if the object can be made immutable. ([Oracle Docs][3])

Given that, there are two broad strategies:

1. **Immutable Pen** — once created, its state can never change. Thread-safe by design. ([Baeldung on Kotlin][4])
2. **Mutable Pen with synchronized access / safe encapsulation** — allow state changes (e.g. capping/uncapping, ink consumption, refill) but guard internal state transitions with synchronization or similar concurrency mechanisms. ([artima.com][2])

Which strategy to use depends on whether your “Pen” needs to change (likely yes — pens are stateful: capped/un-capped, ink level etc.). So usually, a **thread-safe mutable pen** makes sense.

## 📝 Example: Thread-Safe Pen Interface + Implementation in Java

Below is a conceptual design of a “thread-safe pen” in Java. I’ll show:

* An interface `Pen` (unchanged)
* A concrete class `ThreadSafeRefillablePen` that supports capping/uncapping, writing (consuming ink), and refilling — and uses synchronization to ensure thread-safety

```java
public interface Pen {
    String getColor();
    double getTipSize();
    boolean isCapped();
    void cap();
    void uncap();
    void write(String text);
    void refill(double amount);  // optional, may throw if not refillable
    double getInkLevel();        // optional status
}
```

```java
public class ThreadSafeRefillablePen implements Pen {
    private final String color;
    private final double tipSize;
    private boolean capped;
    private double inkLevel;

    // lock object for synchronization
    private final Object lock = new Object();

    public ThreadSafeRefillablePen(String color, double tipSize, double initialInkLevel) {
        this.color = color;
        this.tipSize = tipSize;
        this.inkLevel = initialInkLevel;
        this.capped = true;
    }

    @Override
    public String getColor() {
        return color;
    }

    @Override
    public double getTipSize() {
        return tipSize;
    }

    @Override
    public boolean isCapped() {
        synchronized(lock) {
            return capped;
        }
    }

    @Override
    public void cap() {
        synchronized(lock) {
            capped = true;
        }
    }

    @Override
    public void uncap() {
        synchronized(lock) {
            capped = false;
        }
    }

    @Override
    public void write(String text) {
        synchronized(lock) {
            if (capped) {
                throw new IllegalStateException("Cannot write: pen is capped");
            }
            if (inkLevel <= 0.0) {
                throw new IllegalStateException("Cannot write: no ink left");
            }
            // simulate ink usage
            // e.g. consume ink proportional to text length
            double usage = 0.01 * text.length();  // example ratio
            inkLevel = Math.max(0.0, inkLevel - usage);
            // actual writing logic — e.g. output text somewhere
            System.out.println("Writing \"" + text + "\" using " + color + " pen. Remaining ink: " + inkLevel);
        }
    }

    @Override
    public void refill(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Refill amount must be > 0");
        synchronized(lock) {
            inkLevel += amount;
            // maybe cap to some max, depending on design
        }
    }

    @Override
    public double getInkLevel() {
        synchronized(lock) {
            return inkLevel;
        }
    }
}
```

### Why this is thread-safe

* All mutable state (`capped`, `inkLevel`) is private. External code cannot directly modify them. ([artima.com][2])
* All methods that read or write mutable state synchronize on a private lock object, ensuring that only one thread at a time can modify or read state — avoiding data races. ([artima.com][2])
* The `color` and `tipSize` fields are immutable (final or never changed), so no need to protect them. Read-only fields don’t need synchronization. ([InfoWorld][1])
* By synchronizing only on the critical sections (state mutation/read), we minimize locking overhead compared to synchronizing everything. ([artima.com][2])

## 🎯 Alternative/Advanced Approaches & Tradeoffs

* **Immutable Pen**: If you model a Pen whose state never changes — e.g. just a “blue ballpoint pen with 0.7mm tip” and you don’t model ink depletion/capping — you could make the class immutable. Immutable objects are automatically thread-safe. ([Baeldung on Kotlin][4])
* **Lock-free / atomic variables**: For simple mutable fields (e.g. ink level), you might use atomic types (`AtomicDouble` or `AtomicInteger` if representing discreet ink units) to avoid explicit synchronization, though for multiple fields that must be updated consistently (e.g. ink level + capped state), synchronization is easier and safer. ([GeeksforGeeks][5])
* **Minimizing lock scope**: Only lock what’s necessary (e.g. state changes), avoid holding locks while doing heavy work (like actual writing, I/O) to reduce contention — a common guideline for concurrency-safe design. ([artima.com][2])
* **Document thread-safety**: If this is part of a library or shared codebase, you may want to annotate or document which classes are thread-safe, and under what usage constraints (e.g. `ThreadSafeRefillablePen` is safe for concurrent use). Many frameworks/tools rely on such annotations. ([Reddit][6])

## ✅ Summary — When to Use Which Design

| Scenario                                                                                          | Recommended Design                                                       |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Pen with **fixed properties only** (color, tip size; no ink depletion, no cap/un-cap)             | Immutable Pen class — simpler and thread-safe automatically              |
| Pen with **mutable state** (ink level, cap/un-cap, refill, write) — possibly shared among threads | Mutable Pen with private state + synchronized access (as above)          |
| High performance / high concurrency, simple mutable state                                         | Consider atomic variables or lock-free techniques (if operations simple) |
| Complex operations that combine multiple fields (e.g. ink + cap + maybe tracking usage)           | Use synchronized blocks or lock object to maintain consistency           |
